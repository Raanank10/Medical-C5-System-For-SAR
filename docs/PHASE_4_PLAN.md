# Phase 4 Plan: Split Into Implementation Packages

This is a working plan for `docs/ROADMAP.md` Phase 4, written for a fresh session to pick up with no memory of how it was produced. Phases 1-3 are done (see `docs/ROADMAP.md` and `docs/ARCHITECTURE.md`'s "Backend Deployment Status" for exactly what's real). Phase 4 is a different order of magnitude from anything done so far: it means actually splitting a 10,400-line single-file prototype into real, separately buildable/deployable packages. Read this whole document, and the docs it points to, before writing any code.

## How to Use This Document

- This is a **plan**, not a locked spec. All six original open decisions (mobile framework, command-web framework, monorepo tooling, migration tooling, `services/projectors`' scope, `index.html` retirement timing) were made explicitly with the user before this document's last update — see the Decisions section below for what was chosen and why, and don't re-ask them. This repo's established working pattern (see recent PR history) is: research, present findings, ask before ambiguous/architecturally significant choices, implement, verify live, ship in small focused PRs, wait for explicit merge approval each time. Continue that pattern for anything new that comes up during implementation, not just the six listed decisions — Phase 4 is exactly the kind of work where skipping the "ask" step is expensive to undo.
- Do the sub-phases roughly in order (4A → 4F). Each one is scoped to be its own PR (or several). Don't start 4E/4F before 4A-4D land — the later sub-phases depend on the earlier ones existing.
- **`index.html` (and `demo/rescue-app.html`) must keep working, unmodified in behavior, throughout all of Phase 4** until the explicit retirement decision in 4G. This is not optional scaffolding — it's the only thing anyone can currently demo, and `docs/ROADMAP.md`'s own "Guiding Constraint" says not to let new architecture slow down what already works. Build the new structure *alongside* it, prove it out, and only then talk about retiring the old one.
- Re-run `python scripts/check_repo.py`, `node tests/domain-rules.test.js`, and `npm run test:browser-smoke` before every PR in this phase, same as always — none of this work should be exempt from the existing validation suite, and check_repo.py will need updates as new directories appear (see 4A).

## Decisions

Four of the six original open decisions were made explicitly with the user before any Phase 4 work started (not assumed) — recorded here so a fresh session doesn't re-litigate them:

1. **Mobile app framework: web-based PWA, not Expo/React Native.** Driven by a real, explicit constraint: it must work on both Android and iOS without new recurring cost. Expo/React Native cannot satisfy that — Apple requires a **$99/year Developer Program membership** for any real iOS distribution or even TestFlight testing; there's no free path to real-device iOS beyond a handful of personally-signed 7-day builds. A PWA is genuinely $0 on both platforms (installable via "Add to Home Screen" on iOS Safari, "Install app" on Android Chrome, no store, no account, no fee, ever) and, as a bonus, lets `apps/field-mobile` import `packages/domain` directly with zero cross-language translation, unlike React Native. This does mean field-mobile inherits `docs/FAILURE_MODE_REVIEW.md`'s F2 (browser storage eviction under memory pressure) as a live constraint rather than something a native app would sidestep — plan real IndexedDB usage (not `localStorage`) and accept that as the residual tradeoff for the $0 constraint, don't rediscover it partway through 4F. Two more PWA-specific constraints to design around from the start rather than discover late: mobile OSes can suspend a PWA's background execution at will, so sync correctness must never depend on "the browser kept syncing while closed" — trigger sync on app-open, app-foregrounded, network-restored-while-active, and an explicit manual action, the same way `index.html`'s 45s interval already only runs while the tab is open; and cross-platform push notification support (for a future "RED patient deteriorating" alert, say) is uneven enough between Android Chrome and iOS Safari that it shouldn't be assumed to work uniformly without testing on the exact target devices — not a blocker for Phase 4's scope, just don't build a feature around it without verifying first. Neither of these reopens the PWA-vs-native decision; if field testing later surfaces a real hardware-integration need (BLE sensors, dedicated peripherals) that a browser genuinely can't reach, a native field client can be added later against the same backend/event model/domain package — that's a future option this decision keeps open, not a commitment being made now.
2. **Command-web framework: React.** The whole prototype has been deliberately framework-free vanilla JS (`CLAUDE.md`: "no new production dependencies until there's a clear module boundary") — building `apps/command-web` is exactly that boundary arriving. React was chosen for its dominant ecosystem/hiring pool and mature dashboard/data-table libraries, and it now also has a direct practical payoff: since field-mobile is a PWA (decision 1), it can be built in React too, sharing real patterns and component code between the two apps rather than a React Native/React split.
3. **Monorepo tooling: npm workspaces.** Lowest friction, zero new dependency beyond npm itself, matches this repo's consistent minimal-dependency bias through every phase so far. No build-caching/task-graph tool (Turborepo/Nx) adopted — revisit only if rebuild/test times actually become a real problem once more of the eight targets exist, don't add the tooling preemptively.
4. **Database migration tooling: the Supabase CLI's built-in migration commands** (`supabase migration new`/`up`/`db push`). Least new surface area — directly wraps the same apply/list operations already used via `mcp__Supabase__apply_migration`/`list_migrations` throughout Phases 2-5 — and purpose-built for this project's actual Postgres+Supabase setup.

The final two decisions were also made explicitly with the user, closing out all six original open decisions before any Phase 4 work started:

5. **`services/projectors`' actual scope: just the existing Postgres trigger, no separate deployable service.** `project_patient_state()` (`database/013_consolidate_patient_status_projection.sql`) already does the projection work live and correctly — there is no identified logic today that needs to run outside the database as its own worker/process. Introducing a separate service now would be building infrastructure to satisfy a roadmap bullet's literal wording, not a real requirement. `services/projectors` as a target in `docs/ROADMAP.md`'s list does not get its own directory or deployable in Phase 4; 4D's scope is limited to relocating `services/sync-api`. Revisit only if a real future need for out-of-database projection logic actually appears (e.g. projection work too heavy or too slow for a trigger, or needing to call an external system) — don't build it speculatively.
6. **`index.html` retirement: an explicit sunset once `apps/command-web` and `apps/field-mobile` both reach real feature parity**, not kept indefinitely. "Parity" means each app meets its own sub-phase's acceptance criteria (4E: full command-role parity verified live; 4F: full offline-sync round trip verified live on real Android and iOS devices) — once both are true, `index.html`/`demo/rescue-app.html` get a documented cutover point rather than being left running forever alongside apps that have already caught up to them. Until that point they keep working unmodified, per this document's "How to Use This Document" section.

## Sub-Phases

### 4A. `packages/domain` as a real package

Lowest risk, do this first — it's mostly formalization of something that already works.

- Add a real `package.json` to `src/domain/` (or move to `packages/domain/` — pick one, and update `tests/domain-rules.test.js`'s import path and `scripts/check_repo.py`'s `DOMAIN_RULES_FACTORY_MARKER` sync-check accordingly).
- **Do not remove or change the inline-copy-plus-drift-check pattern in `index.html`/`demo/rescue-app.html`.** That's how the no-build-step prototype consumes this logic today, and it must keep working. The new package is for the *new* apps (4E/4F) to import normally; the prototype keeps its manual-sync copy.
- Acceptance: `tests/domain-rules.test.js` still passes unmodified in behavior, `check_repo.py`'s domain-rules drift check still catches a deliberately-introduced mismatch (verify this, don't assume the path change didn't silently break the check), and the package is importable via a normal `require`/`import` from a throwaway Node script outside `src/`.

### 4B. `packages/fixtures` — reconcile two demo-data generators into one

Real design work. `index.html`'s `loadDemoScenario()` (JS, in-memory objects matching the client's patient shape) and `seed_demo_db.py`'s `SCHEMA`/data (Python, SQLite rows matching the analytics schema) currently describe *the same conceptual demo incident* in two disconnected, hand-maintained implementations.

- Options to evaluate (don't default to the first one without comparing): (a) one JSON/YAML fixture format that both a JS loader and a Python loader read, (b) generate one from the other at build time, (c) leave them separate but document why they're allowed to diverge. Given `docs/OPERATIONS_SAFETY.md`'s synthetic-data-only rule applies to both, and `scripts/check_repo.py`'s drift-detection precedent for domain rules, a shared-source-of-truth approach (a) is the most consistent with how this repo already handles the "two copies of the same logic" problem — but verify the actual field sets line up closely enough to make that worthwhile before committing to it.
- Acceptance: both `index.html`'s demo mode and `seed_demo_db.py`'s output are verifiably generated from (or checked against) the same fixture source, not just visually similar.

### 4C. `database/migrations` — real migration tooling

- Use the Supabase CLI's built-in migration commands (decision 4 above — already settled, don't re-ask). Convert the numbered SQL files (now 29, `001` through `029`) into that tool's format without changing their content or order — this is a mechanical wrapping, not a rewrite. `database/001_postgresql_schema_v1.1.sql`/`archive/v0.6`/`archive/v0.7` stay as historical archive, not converted (per `CLAUDE.md`: "Preserve historical versions under `archive/` rather than deleting superseded docs/schema").
- Acceptance: applying the full migration history to a fresh empty Postgres database via the new tool produces a schema equivalent to the current live Supabase project's schema (verify with a real diff, not by eye — `information_schema` comparison or `pg_dump --schema-only` on both sides).
- **Attempted and blocked in the sandbox environment used for the audit/retention work (2026-08).** The Supabase CLI itself is available with no new persisted dependency (`npx supabase --version` → `2.115.0`), but verifying the acceptance criterion needs one of two things, and neither was available:
  - `supabase start`'s local Postgres+Docker stack — blocked because the Docker daemon can't run in that sandbox (`sudo service docker start` fails with a container-in-container `ulimit: Operation not permitted` error; the `docker` client itself is present, just nothing to talk to).
  - `supabase link` against the live/a remote project for CLI-based verification — blocked because no `SUPABASE_ACCESS_TOKEN` (or equivalent) was available in that environment (`env | grep -i supabase` empty).
  - Given both verification paths were unavailable, the mechanical rename of all 29 files was **not** performed rather than doing it unverified — a rename with no real diff to confirm equivalence would just trade a known-good hand-applied history for an unverified one, on a live project with real RLS/data behind it. This is an environment constraint, not a decision that the conversion itself is wrong or should be skipped — a session with a working Docker daemon (or a CLI access token) should redo this evaluation and, if it verifies clean, do the conversion.

### 4D. `services/sync-api`

`services/projectors` (Decision 5) is not part of this sub-phase's scope, or any sub-phase's: it's settled as "just the existing `project_patient_state()` Postgres trigger, no separate deployable service" — no directory or new code to write for it.

- **Real constraint to solve first**: the Supabase CLI requires Edge Functions to live at `supabase/functions/<name>/` to deploy them. Moving `supabase/functions/sync-log/` to `services/sync-api/` outright would break `supabase functions deploy` unless the CLI is reconfigured or a symlink/build-copy step is added. Resolve this concretely (test an actual deploy from the new location, don't assume) before moving anything.
- Acceptance: a real deploy of the relocated function succeeds and passes the same live verification this session used for `sync-log` (push/pull round trip, idempotent duplicate resubmission, a blocked-dependency case) — don't take "the code compiles" as sufficient.

### 4E. `apps/command-web` — build before field-mobile

Command-web is the better first real app to build: no offline-first requirement, and the backend it needs (`get_incident_command_state` RPC, `device_presence`, projected `patients` reads, `sync_ingestion_errors`) is already real, RLS-scoped, and consumable directly via a normal Supabase JS client — no new backend work required to get started.

- Scope: the pc/cc/chamal/logistics command views currently in `index.html` (`renderCommander`, `renderCcHeroDashboard`, `renderLogisticsOfficer`, the command panels built this session — device presence, server-state snapshot, poison-event/high-risk review).
- `docs/CONFLICT_RESOLUTION_DECISION.md`'s F3 resolution is **already built**, ahead of this sub-phase, per the user's explicit choice — `database/019`-`021` shipped the `physician`/`paramedic` roles, their RLS, and `project_patient_state()`'s field-level projection rework with the role-authority tie-break (physician > paramedic > cc > pc > medic), live on the deployed Supabase project. `apps/command-web` should consume this real mechanism (the `conflict_log` rows it writes, the `sync-log` push response's `field_conflicts` field) rather than needing to design it from scratch — see `index.html`'s `pullFieldConflicts()`/`patientHasFieldConflict()` for the reference client-side read pattern to port over.
- Build in React (decision 2 above — already settled, don't re-ask).
- Acceptance: feature parity with `index.html`'s command views for at least one full role (recommend `cc`, since it has the richest panel set), verified against the same live Supabase project, not a mock.

### 4F. `apps/field-mobile` — do this last

The hardest, highest-risk piece: offline-first local persistence, background sync, MSTART sweep flow, gloved/one-handed UX, real device presence/heartbeat. Do this after 4A-4E so the domain package, migration tooling, and sync-api relocation are already proven, and after building command-web has surfaced real lessons about the chosen monorepo/build tooling under lower stakes.

- Build as a web-based PWA, in React to match `apps/command-web` (decision 1/2 above — already settled, don't re-ask; the $0-on-both-platforms constraint is why PWA won over Expo, see the Decisions section).
- Use IndexedDB for local persistence, not `localStorage` — this is the real reason a PWA needed deciding first: `docs/FAILURE_MODE_REVIEW.md`'s F2 (storage eviction under memory pressure) is a live constraint for a web app in a way it wouldn't be for a native app, so don't default to copying `index.html`'s `localStorage` pattern just because it's familiar.
- Trigger sync explicitly on app-open, app-foregrounded, network-restored-while-active, and a manual action — never design correctness around the assumption that a mobile OS lets a PWA keep syncing in the background (Decision 1). This matches `index.html`'s existing 45s-while-open interval; field-mobile just needs to be deliberate about the same constraint rather than assuming a service worker can be relied on to keep running.
- Scope: everything currently in `index.html`'s medic-facing flows (Quick/Extended patient creation, the legacy step-based flow, vitals/tourniquet timers, the local outbox/sync push-pull, `device_presence` heartbeat).
- Acceptance: a full offline round trip (create a patient with no network, reconnect, verify it syncs and appears via `pullProjectedPatientState` on a second device) works end to end on a real Android and a real iOS device via "Add to Home Screen"/"Install app" — not just in a desktop browser tab, since the PWA install path itself is part of what needs verifying.

### 4G. Retirement (not a build sub-phase)

Decision 6 is already settled: once 4E and 4F are each at real, verified feature parity with their corresponding slice of `index.html` (per their own acceptance criteria above), `index.html`/`demo/rescue-app.html` get an explicit, documented sunset — not kept indefinitely, and not silently abandoned either. Don't let the cutover happen by neglect: when both sub-phases hit parity, write down the actual cutover point (what stops being maintained, from when) as its own change, the same way every other decision in this document got written down.

## Risks Specific to This Phase

- **Silent behavior drift between `index.html` and the new apps.** The single biggest way this phase could go wrong: `apps/command-web`/`apps/field-mobile` reimplementing triage/vitals/handover logic slightly differently than `index.html`, with nothing catching the divergence. `packages/domain` (4A) exists specifically to prevent this for the rules it covers — make sure every new app actually imports it rather than re-deriving similar-looking logic, and extend `scripts/check_repo.py`-style drift detection to cover the new apps if there's ever a second inline copy of anything.
- **RLS/authorization gaps recurring in new code paths.** `docs/THREAT_MODEL.md`'s T1 names this as the most concrete, evidenced risk in the codebase — four real instances were found in Phase 3 alone, each incidentally. New apps calling the database directly (rather than through `index.html`'s already-audited call sites) is exactly the kind of new surface where a fifth instance would appear. Budget real review time for this, don't assume RLS "just works" because it worked for the prototype.
- **Scope creep into a full rewrite.** Phase 4 is a split, not a rewrite — behavior, terminology, and role/command logic should carry over from what's documented in `docs/C5_SENTINEL_SAR_MVP_SPEC_v1.2.md`, `docs/API_SURFACE_v1.2.md`, `docs/ROLE_COMMAND_MODEL_v2.8.md`, and `docs/TACTICAL_UI_GUIDELINES.md`, not get "improved" opportunistically along the way. If something genuinely needs to change, that's a separate, explicit decision with the user, not a side effect of restructuring.

## Definition of Done for Phase 4

All of: `packages/domain` is a real importable package with `index.html` still working unmodified via its own synced copy; `packages/fixtures` has one reconciled source of demo data; `database/migrations` runs the full schema history through real migration tooling with a verified-equivalent result; `services/sync-api` is deployed from its new location and re-verified live (with no separate `services/projectors` built, per Decision 5); `apps/command-web` has real feature parity for at least one command role against the live backend; `apps/field-mobile` has a real verified offline-sync round trip; and `index.html`'s sunset (4G, per Decision 6) has an actual documented cutover point once that parity is reached, not left indefinite by default.
