# Structured Logging / Observability Review

`docs/ROADMAP.md` Phase 5 / `docs/PRODUCTION_READINESS.md`'s open item: "no centralized structured-logging/observability system has been reviewed." This is that review — what exists today (checked against the real live project, not assumed), the realistic options, and a recommendation. Not a request for external sign-off like the clinical-governance or field-validation items in the same phase; this is a technical decision this repo can make and revisit like any other engineering choice.

## What exists today (verified against the live project, 2026-08)

**Domain-specific audit tables** — real, working, and already reviewed elsewhere in this repo: `conflict_log`, `sync_ingestion_errors`, `watchdog_alerts`, `retention_actions` (new, `database/028`). Each is RLS-gated, queryable, and has a dedicated command-view review panel. These are *structured*, but each is purpose-built for one domain concept (a sync rejection, a role-authority tie-break, a watchdog trigger) — none of them is a general-purpose application log, and none was designed to capture "something unexpected happened in this Edge Function" or "the client hit an uncaught JS error."

**Supabase platform logs** — real infrastructure, already running, zero app code required: `edge_logs`, `postgres_logs`, `postgrest_logs`, `pgbouncer_logs`, `realtime_logs`, `storage_logs`, `workflow_run_logs`, queried live via `mcp__Supabase__query_logs` (ClickHouse SQL over a unified log stream, 24h window per query) or the Supabase dashboard's Logs Explorer. Checked live: `edge_logs` for this project currently carries only Supabase management-plane health-check traffic (`GET /auth/v1/health`, `HEAD /rest-admin/v1/ready`) — no invocation-level detail for either deployed Edge Function, because neither one writes anything. This tier is real and free, but two gaps limit it: (1) nothing app-level is in it yet (see next finding), and (2) it's only reachable via Supabase project-owner credentials (dashboard login or MCP) — no command-role user inside the app itself can see it, unlike the in-app quarantine/conflict review panels.

**Edge Functions have zero logging.** Checked both deployed functions directly: `supabase/functions/sync-log/index.ts` and `supabase/functions/handover-consume/index.ts` contain no `console.log`/`console.error`/`console.warn` calls at all. Every branch — including genuine server-side failures (an unexpected exception before the first `try`/`catch`, a Postgres error surfaced as a 500) — returns an HTTP response with no corresponding log line anywhere. If a sync push fails for a reason not already covered by the `sync_ingestion_errors` quarantine path (e.g. an actual outage, an auth-provider blip, an unhandled exception), there is currently no record of it anywhere, in-app or in the platform logs, beyond whatever HTTP status the client happened to observe.

**Client has no error-reporting pipeline.** Checked `index.html` (~8,600 lines): exactly one `console.error` call in the entire file (inside the local-persistence write queue), no `window.onerror` handler, no `unhandledrejection` handler. An uncaught exception on a real medic or command device today is silently lost — invisible to the device operator (no toast/log surface), invisible to command (no sync event exists to carry it), invisible to whoever might debug it after the fact (nothing left on disk or server).

## Options

**A. Zero-dependency baseline: structured logs in the two Edge Functions + a client-side uncaught-error hook.** Add `console.log(JSON.stringify({...}))` at the real decision points already in `sync-log`/`handover-consume` (batch-level push/pull summaries, unexpected-error branches) — this is immediately captured by the already-running `edge_logs` tier for free, no new service, no new dependency, matches this repo's "no new production dependencies" convention (`CLAUDE.md`). A client-side `window.onerror`/`unhandledrejection` handler is a second, separable piece: capturing an error is easy, but *where it goes* is a real design decision (a new sync event type mixes debug/crash data into the clinical event log that `docs/AUDIT_AND_RETENTION_POLICY.md` explicitly treats as a distinct, more sensitive category from operational data — deliberately not decided here, see Recommendation below).

**B. External observability platform** (Sentry, Better Stack, Axiom, Datadog, etc.). Real capability this repo genuinely lacks — alerting/paging, cross-service correlation (client JS error ↔ the sync push that triggered it ↔ the DB row it touched), retention beyond Supabase's own window, dashboards. Real cost too: a new dependency, a new external account/API-key-management story (another secret alongside the service-role key, another entry in `docs/THREAT_MODEL.md`), and genuine ongoing spend. Premature before Phase 4 produces real deployable services with an actual on-call story behind them — adopting this now would be building monitoring for a system that doesn't have anyone monitoring it yet.

**C. Extend the existing Postgres-audit-table pattern to a general `app_log`/`client_error_log` table**, following the same RLS + command-panel-review convention already used for `conflict_log`/`sync_ingestion_errors`/`retention_actions`. No new dependency, fits existing conventions exactly, keeps client error visibility inside the app itself (a real advantage over Option A/B for a command role with no Supabase dashboard access). Real downside: Postgres isn't built for high-frequency log-volume writes the way a dedicated log store is (write amplification on every row, no built-in rotation) — would need its own retention plan (the same Class-C-style "audited redaction" pattern `database/028` already established) before it's safe to point at a chatty source like every client-side warning.

## Recommendation

Implement Option A's Edge Function half now — it's the only piece with zero design risk and zero new decisions: no schema change, no new table, no new dependency, and it turns already-running, already-free platform logs from carrying nothing to carrying real diagnostic detail. Done as part of this review (see `supabase/functions/sync-log/index.ts` and `supabase/functions/handover-consume/index.ts`): structured JSON log lines at genuine decision points (push/pull batch summaries, malformed-body/unexpected-error branches), logging counts, codes, ids, and roles only — never patient names, free-text clinical fields, or handover secrets/hashes.

Deliberately **not** implemented here: the client-side error-capture hook (Option A's other half) and Option C. Both require picking where client-side errors actually go, which is a real data-model decision (new event type vs. new table vs. something else, plus a retention story once it exists) that deserves its own scoped pass rather than being folded into a "review logging options" task. Option B stays out of scope until Phase 4 gives this project real deployable services and an operational story to monitor.
