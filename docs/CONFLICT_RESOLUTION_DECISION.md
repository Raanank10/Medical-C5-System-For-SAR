# Decision: Cross-Device Concurrent-Edit Resolution (F3)

**Status: built.** The choice among A-D below belonged to the user, per this repo's established pattern (`docs/PHASE_4_PLAN.md`: "ask before ambiguous/architecturally significant choices") — the user chose a hybrid of A, B, and C. The user later chose to build it now, ahead of Phase 4, rather than deferring it to the `apps/command-web` split — `database/019_add_physician_paramedic_enum_values.sql`, `database/020_physician_paramedic_rls.sql`, and `database/021_field_level_conflict_resolution.sql` are the real schema/trigger implementation, live on the deployed Supabase project. See "Decision" below for the mechanism, and "Physician-role prerequisite" for how the one open gap was resolved.

## The problem

`docs/FAILURE_MODE_REVIEW.md`'s F3 describes the current, real behavior: `pullProjectedPatientState`'s "local edit wins until pushed" rule is evaluated **per device, against that device's own outbox only**. It has no visibility into another device's concurrent edit.

Concretely: two devices (two medics, or a medic and a `pc`) each have a genuinely concurrent unsynced edit to the same patient — say Device A logs a triage override to red while Device B logs a medication administration. Both push independently. For fields `project_patient_state()` treats as single-column overwrites (`current_triage`, `current_status`), whichever event's trigger fires last on the server wins. Nothing is merged, nothing is surfaced to either medic, and the loser's specific intent (the triage override, in this example) is gone from projected state — though it's worth noting the *event itself* is never lost; it's still in the append-only event log and AAR timeline, just not reflected in the live projected `current_triage`.

`conflict_log`/`PATIENT_EDIT_CONFLICT_DETECTED` already exist, but only catch same-device conflicts (e.g. two browser tabs on one device comparing `lastModifiedAt` at open vs. save time) — not this cross-device case.

This is exactly the scenario `docs/FIELD_USABILITY_TEST_PLAN.md` Session 2 step 4 is designed to deliberately stage, and Session 4 (full MCI rehearsal) is likely to surface it naturally. A real drill run is evidence for this decision, not a substitute for making it — the drill can confirm the current silent-overwrite behavior actually happens as described, but it can't choose the right fix; that's a product call about what should happen when two medics genuinely disagree about a patient's status within the same ~45-second window.

## Options

**A. Last-write-wins, but surfaced.** Keep the current overwrite behavior for the projected single-column fields, but write a `conflict_log` entry (or a new event type, e.g. `PATIENT_FIELD_CONFLICT_DETECTED`) whenever `project_patient_state()`'s trigger overwrites a field that another event touched within a short window (e.g. 2 minutes). The command view surfaces this as a flag on the patient card. Nothing blocks either medic in the moment; the conflict becomes visible after the fact, to a `pc`/`cc` who can follow up. Lowest engineering cost, closest to current behavior, but still means a real triage override can be silently overwritten *from the acting medic's own point of view* until someone downstream notices the flag.

**B. Field-level, not row-level, merge.** Instead of one event's trigger overwriting the whole `current_triage`/`current_status` column, project a small ordered history per field (e.g. keep the last N triage-setting events per patient) so the server can distinguish "these two events touched different fields, both can apply" from "these two events touched the *same* field, one must win." Reduces false conflicts (the example above — a triage override and a medication administration — wouldn't need to conflict at all under this model, since they touch different fields) but is real schema/projection work, not a policy choice layered on top of what exists.

**C. Authority ordering.** Define an explicit priority order among roles/event types for genuinely same-field conflicts — e.g. a triage override from a `cc` always wins over one from a `medic`, or an explicit `PATIENT_TRIAGED_EXPECTANT` always wins over any other triage event regardless of timing. Requires deciding and documenting a real clinical/command authority hierarchy (touches `docs/ROLE_COMMAND_MODEL_v2.8.md` and possibly `docs/CLINICAL_GOVERNANCE_REVIEW_FRAMEWORK.md`'s domain, since it's encoding who is allowed to overrule whom, not just a data-merge rule) — the highest product complexity of the three, but the only one that reflects "some overrides should always win" rather than treating every conflict as a tie broken by timing.

**D. Do nothing new — accept current behavior, document it as a known limitation.** Keep last-write-wins with no surfacing beyond what `docs/FAILURE_MODE_REVIEW.md` already documents. Only defensible if the field usability drill (Session 2/4) shows this scenario is rare enough in practice, or severe enough consequences are judged acceptable at this prototype stage — this option itself needs the drill's evidence to justify, not just default inertia.

These aren't mutually exclusive in sequence — A is a reasonable interim step even if B or C is the eventual target, since it's the cheapest way to stop the failure from being *silent* while a fuller fix is designed.

## Decision

A hybrid of A, B, and C — not any single option alone:

- **B provides the mechanism.** `project_patient_state()` stops treating `current_triage`/`current_status` as single-column overwrites and instead tracks which specific fields each event touches, so two genuinely independent edits (a triage override and a medication administration, in this doc's running example) never conflict at all — they touch different fields and both apply cleanly. This is the real schema/projection work the original write-up flagged as the highest-cost option; it's chosen anyway because it's what actually eliminates most false conflicts rather than just resolving them after the fact.
- **C provides the tie-break for what's left.** Once B is in place, only genuine same-field collisions remain (two devices both setting `current_triage` in the same window). Those are resolved by role authority order, decided by the user: **physician > paramedic > cc > pc > medic** — the user added `paramedic` to the ranking when resolving the physician-role prerequisite below, ranked as a clinical-seniority tier just under physician. A higher-authority role's edit to the same field always wins, regardless of which event's trigger happened to fire last on the server, as long as the two edits fall within a 5-minute collision window of each other (`app.resolve_field_authority()`, `database/021`) — outside that window it's treated as a legitimate later reassessment and falls back to plain last-write-wins, so an old authority edit can never permanently freeze a patient's state against real newer data. The 5-minute window is a reasoned starting default (client syncs every 45s plus offline-reconnect slack), not something this decision pinned exactly — adjustable from real field-drill data (`docs/FIELD_USABILITY_TEST_PLAN.md`).
- **A provides the transparency layer on top.** Whenever C's authority rule causes an override — i.e. a lower-authority edit to a field loses to a higher-authority one — that event is written to `conflict_log` as a `PATIENT_FIELD_CONFLICT_DETECTED`-tagged row (`app.log_field_authority_conflict()`) and surfaced as a flag on the patient card plus a review-panel entry in the command view. The overridden medic's action is never silently lost from view, even though there's still always one deterministic winner and no real-time merge UI. Equal-rank genuine collisions (e.g. two medics, same field, same window) are also logged, at lower severity, on the reading that "surfaced, not silent" applies to any real silent-loss case, not only authority-decided ones.

**Scope note**: the field-level mechanism only routes `PATIENT_TRIAGE_UPDATED`/`PATIENT_STATUS_UPDATED` through the authority tie-break — `PATIENT_TRIAGED_EXPECTANT`, `PATIENT_HANDED_OVER`, and the treatment-implied `stabilizing` status write keep their pre-existing guards unchanged. Those are lifecycle-terminal or side-effect writes, not the deliberate concurrent field edits this decision's running example (triage override vs. medication administration) describes.

## Physician-role prerequisite — resolved

The chosen authority order originally named "physician" at the top with no such role in the live `user_role` enum — "physician" (`רופא / פראמדיק`) existed only as a client-side-only dashboard label (`activeRoleDashboard==='doctor'` in `index.html`), with no corresponding authenticated server role, RLS treatment, or `profiles.role` value.

Resolved by adding **two** real server roles, not one: `physician` and `paramedic` (`database/019_add_physician_paramedic_enum_values.sql`). `physician`'s RLS scope mirrors `cc`'s command-adjacent scope (`app.is_command_role()`, `app.can_access_incident()`) plus clinical/first-responder event-write access (`cc` itself has none, which would otherwise leave physician unable to ever participate in the triage/status tie-break this whole feature exists to build — see `supabase/functions/sync-log/index.ts`'s `ROLE_ALLOWED_EVENT_TYPES.physician`). `paramedic` is an exact mirror of `medic`'s scope (`app.can_write_clinical_event()` and every RLS policy `medic` appears in, including `patients_insert`) — a clinical-seniority label for the tie-break ranking, not a new capability tier. Client-side, `physician` maps onto the existing `doctor` dashboard (`SERVER_ROLE_TO_CLIENT_ROLE`); `paramedic` needs no remap and reuses the medic field workflow screen directly.

## Paramedic/physician clinical-authority parity

Follow-up decision from the user, after the roles above shipped: **paramedic should have the same field/clinical authority as physician — same drugs and procedures — with the single exception of official death certification, which stays physician-only.** Scoped deliberately narrow, per the user's explicit choice: this is about *clinical event-write authority*, not physician's broader command-adjacent RLS scope (incident/sector management, device presence, patient identity, blanket incident access) — paramedic stays a field role, it does not become a second `cc`-equivalent.

- **Drugs/procedures**: `paramedic` and `physician` already shared the full `CLINICAL_EVENTS`/`FIRST_RESPONDER_EVENTS` event-type list from the original build (medication, tourniquet, airway management, treatment interventions) — no change needed there. One real gap found and fixed: `high_risk_override_insert` (confirming a high-risk clinical override, e.g. a pediatric medication dose outside the normal safe range) only allowed `medic`/`pc` — `paramedic` had been missed in `020` despite that migration's own header comment saying it should be included, and `physician` had never been added at all. Fixed in `database/023_high_risk_override_add_physician_paramedic.sql`, verified live.
- **Official death certification**: the app's death-certification workflow (`doctor_death_cert` reinforcement requests, `DOCTOR_DEATH_CERTIFICATION_REQUESTED`) is currently a client-side-only narrative demo concept — it's not a real server event type, has no RLS, and has no functional "resolve/certify" action anywhere in the code today (confirmed by inspection — `renderDeathCertificationChain()` only renders a static explanatory chain). There is nothing to restrict yet at the code level; this is recorded here so whoever eventually builds a real death-certification action knows it should stay physician-only, unlike the field-level "suspected deceased / black triage" tag (`PATIENT_TRIAGED_EXPECTANT`), which every clinical role (including paramedic) can already set today and continues to be able to — that tag was never the official act (`docs/ROLE_COMMAND_MODEL_v2.7.md`: "the medic is recording field status, not making official death certification").
- **F3 tie-break rank unchanged**: `physician`(5) still ranks above `paramedic`(4) for the role-authority conflict tie-break (`app.role_authority_rank()`) — per the user's explicit choice, clinical-authority parity for *writing* events is a separate question from who wins a same-field collision, and physician keeps final say there, consistent with physician owning death certification.
